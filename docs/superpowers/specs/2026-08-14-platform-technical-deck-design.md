# RKNode 技术方案 PPT 重写设计

## 1. 目标

基于当前项目实现重写 `docs/RKNode平台介绍与节点数据流.pptx`，用于技术方案汇报。
演示文稿以平台架构、节点直连、模型生命周期、RK3588 推理数据面和可靠性机制为主，
不写成产品营销稿或逐命令部署教程。

## 2. 受众

主要受众为需要评审平台技术方案的架构师、研发、交付和技术管理人员。读者了解容器、
模型训练和边缘推理基本概念，但不要求预先熟悉本项目代码。

## 3. 交付范围

- 修改 `scripts/generate_platform_ppt.py`，作为演示文稿的唯一生成源。
- 更新 `docs/ppt-assets/` 中实际用于演示的当前平台截图。
- 重新生成 `docs/RKNode平台介绍与节点数据流.pptx`。
- 保持 16:9 比例和 16 页左右的汇报长度。
- 保留现有视觉体系，但重写页面叙事和技术内容。

## 4. 非目标

- 不在 PPT 中加入可直接使用的生产地址、Token、账号、密码或私钥。
- 不把旧 Worker/Agent 拉取模式作为新部署主线。
- 不把部署手册中的完整命令复制到幻灯片。
- 不把未完成目标板真实流验收的能力描述为已现场验收。
- 不修改平台业务代码或运行时协议。

## 5. 事实来源

内容冲突时按以下顺序判断：

1. 当前后端、节点服务、推理 Agent 和 C++ 管线实现。
2. `.trellis/spec/backend/direct-node-contract.md`。
3. `.trellis/spec/backend/rk3588-media-runtime-contract.md`。
4. 当前 Compose、Dockerfile、离线脚本和环境示例。
5. 当前任务 PRD、设计及验收状态。
6. 现有 PPT 和历史截图，仅作为视觉参考。

## 6. 十六页结构

1. 封面：RKNode RK3588 模型全生命周期平台。
2. 平台定位：中央控制面连接异构执行节点。
3. 完整闭环：数据集、训练、转换、发布、下发和推理。
4. 部署拓扑：Web/API、训练、转换和推理节点。
5. 直连节点协议：身份、能力、健康、容量与鉴权。
6. 训练调度：Torch/Paddle、CPU/CUDA 的指令与数据流。
7. 数据集与训练产物：格式识别、日志、指标、权重和 ONNX。
8. RKNN 转换：Toolkit2、量化、板端验证和部署就绪。
9. 不可变 Release：制品、SHA256、适配器和输入输出契约。
10. Desired Revision：多板下发、原子切换和回滚。
11. RK3588 数据面：RKMPP、RKNN 和 ByteTrack。
12. 业务分析：二级推理、区域、越线、OSD 和事件媒体。
13. 统一结果：JSONL、HTTP、Kafka、ZLM SEI 和预览。
14. 可靠性：幂等调度、缓存清理、恢复和最终收敛。
15. 部署与安全：在线/离线镜像、Compose、Token、VPN/SSH。
16. 核心价值与技术边界。

## 7. 关键技术叙事

### 7.1 控制面

中央平台持有数据集、任务、模型 Release、节点配置、部署批次和 desired state。浏览器只
访问中央平台。新节点使用直连模式，中央通过节点独立 Token 主动探测、下发和清理。

### 7.2 训练与转换

训练节点覆盖 Torch/Paddle 和 CPU/CUDA。中央下发轻量任务标识，节点按授权回源获取数据，
并回传日志、指标和制品。RK3588 转换节点使用 Toolkit2 完成 ONNX 到 RKNN、量化、板端
Runtime 验证和部署就绪判定。

### 7.3 发布与下发

推理任务引用不可变 Model Release，而不是任意 RKNN 文件。期望版本包含主模型、所有二级
模型、manifest、SHA256 和任务配置。节点全量下载、校验和探测后才原子切换；失败保留
current/previous。

### 7.4 推理数据面

主流程表达为：

```text
RKMPP/OpenCV Capture -> Primary RKNN -> ByteTrack
-> Secondary RKNN -> Analytics -> OSD/Event Media -> Outputs
```

未启用的业务节点从图中省略。二级推理为非人脸用途。区域/越线以跟踪 ID 驱动，事件输出
支持 JSON、JPEG 抓拍和可用时的前后录像。

### 7.5 输出边界

JSONL、HTTP、Kafka 和 ZLM SEI 共用统一结构化协议。预览是独立尽力而为旁路，限频 JPEG
上传中央，浏览器通过短时会话查看。完整视频和业务结果默认留在板端或业务系统。

## 8. 视觉设计

- 深色封面和结尾，中间页面使用低噪声浅色背景。
- 青色代表中央控制面，蓝色代表训练与数据，琥珀色代表转换，珊瑚色代表推理数据面，
  绿色代表健康、完成或恢复。
- 架构图、时序图和数据流图优先于大段文字。
- 每页一个中心结论，页内标题使用紧凑字号，避免装饰性卡片嵌套。
- 图形使用稳定尺寸和对齐网格，所有文字必须在 16:9 页面内完整显示。

## 9. 截图策略

- 使用当前运行平台重新截图，不继续使用带旧日期和旧节点状态的画面。
- 截图至少体现当前已配置的 CPU 训练、RK3588 转换和 RK3588 推理节点。
- 截图不显示真实 Token、SSH 配置或敏感基础设施信息。
- 技术页以架构图为主，截图只作为当前实现证据，不承担核心协议说明。

## 10. 环境与端口表达

- Web 入口描述为可配置，当前部署为 `5173`。
- 中央内部 API、训练节点、转换节点和推理节点端口分别说明职责，避免把临时隧道地址
  误写成固定产品协议。
- VPN 和 SSH 隧道只说明跨网络直连的实现选择，不显示当前真实地址。

## 11. 能力状态表达

以下能力标记为已实现：

- 直连训练、转换和推理节点。
- Torch/Paddle、CPU/CUDA 训练镜像矩阵。
- RKNN 转换、验证报告、Release 和 desired revision。
- RKMPP、RKNN、ByteTrack、NPU Core 策略和独立预览。
- 非人脸二级推理、区域/越线、OSD、事件抓拍/录像。
- JSONL、HTTP、Kafka 和 ZLM SEI 输出。
- 在线与完全离线镜像部署、版本化升级和回滚。

以下内容明确标记为目标环境最终验收项：

- 至少一条真实文件流或 RTSP 的硬解码、NPU 推理、跟踪、业务分析、预览和结构化输出。
- 外部 Kafka 消费者和 ZLM 端到端媒体/SEI 联调。

## 12. 验证标准

- 生成脚本无语法错误并可连续运行两次。
- PPTX 固定为 16 页，标题、页码和页脚一致。
- 页面文本不包含旧日期、过时端口主张、旧注册主线或敏感信息。
- PPTX 能被 LibreOffice 或等效工具无错误打开并导出 PDF。
- 渲染后的每页无文字溢出、重叠、截断、空白截图或图形越界。
- 提取全部页面文本后，当前项目的直连节点、完整推理图、业务分析、输出协议和验收边界
  均有明确覆盖。
