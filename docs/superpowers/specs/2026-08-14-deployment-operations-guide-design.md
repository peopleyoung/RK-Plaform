# RKNode 部署运维手册重写设计

## 1. 背景

当前项目同时存在根目录 `README.md`、`docs/simple-node-deployment.md`、
`docs/offline-deployment.md` 和 `docs/system-guide.md`。这些文档分别覆盖快速开始、
节点部署、离线部署和完整系统说明，但部署步骤存在重复，首次部署人员需要在多份文档间
切换，且部分镜像版本示例容易随发布演进而失效。

本次重写以 `docs/system-guide.md` 为唯一完整部署与运维主手册。其他文档继续作为专题参考，
不在本次范围内删除。

## 2. 目标读者

主要读者为首次部署和后续维护 RKNode 平台的运维人员。手册假定读者具备 Linux、Docker
和基本网络排查能力，但不要求熟悉项目内部实现。

## 3. 目标

- 给出从空白主机到可执行端到端推理任务的完整部署顺序。
- 覆盖中央服务、Torch/Paddle、CPU/CUDA、RK3588 转换与推理节点。
- 覆盖在线源码构建、预构建镜像和完全离线部署。
- 覆盖局域网直连、VPN 和 SSH 隧道三种网络模式。
- 对每个关键步骤提供可执行命令、配置说明、成功判定和失败处理。
- 覆盖旧容器、旧镜像和构建缓存清理，以及升级、回滚、备份和日常运维。
- 使用仓库中的真实 Compose 文件、脚本、环境变量和健康检查作为命令依据。

## 4. 非目标

- 不把手册改写成面向业务用户的页面功能说明。
- 不展开训练算法、模型结构或前后处理实现细节。
- 不记录当前服务器的真实地址、账号、令牌、密码或私钥。
- 不删除或合并现有专题文档。
- 不将尚未完成真实板卡验证的场景描述为已验收能力。

## 5. 信息来源和优先级

发生冲突时按以下顺序确定手册内容：

1. 当前仓库中的 Compose、Dockerfile、`.env.example` 和部署脚本。
2. 服务代码中的环境变量、接口路径和健康检查实现。
3. 已完成的实际部署与验收结果。
4. 现有专题文档中的背景说明和故障处理经验。

镜像版本使用显式变量或发布版本示例，不以 `latest` 作为生产部署默认值。预构建镜像章节
必须区分“本机已有镜像”和“需要重新构建或导入镜像”两种情况。

## 6. 文档结构

正式手册按以下顺序编排：

1. 文档定位与部署架构
2. 组件、端口和数据流说明
3. 部署前检查
4. 获取源码与准备配置
5. 清理旧容器、旧镜像和构建缓存
6. 构建并启动中央服务
7. 部署 Torch CPU 训练节点
8. 部署 Torch CUDA 训练节点
9. 部署 Paddle CPU/CUDA 训练节点
10. 部署 RK3588 模型转换与推理节点
11. 节点注册与网络连通
12. VPN 和 SSH 隧道部署
13. 完全离线环境打包与部署
14. 端到端业务验收
15. 日常运维、升级、回滚、备份和清理
16. 故障排查
17. 配置项、端口和命令速查表

正文按首次部署顺序展开。专题部署方式放在主线之后，避免首次部署人员过早进入网络和离线
部署分支。

## 7. 部署路径设计

### 7.1 在线源码构建

- 中央服务：`deploy/compose.yaml`
- 训练节点：`deploy/nodes/trainer/compose.yaml`
- CUDA 训练叠加：`deploy/nodes/trainer/compose.cuda.yaml`
- Torch/Paddle：通过对应 Dockerfile、基础镜像和环境变量选择
- RK3588 转换与推理：`deploy/nodes/rk3588/compose.yaml`

### 7.2 预构建镜像部署

流程固定为检查镜像架构与标签、备份配置、停止旧容器、加载或拉取新镜像、按服务重建、
健康检查、业务验收和清理悬空资源。具名卷默认保留。回滚通过恢复旧镜像标签并重建目标
服务完成。

### 7.3 完全离线部署

联网环境负责构建镜像、生成离线包和摘要；离线环境负责校验、加载镜像、准备 `.env`、
运行 `deploy/offline/common/` 中的部署与验证脚本。中央服务、四类训练组合以及 RK3588
转换/推理分别给出命令。

## 8. 命令写作规范

每个命令块前明确：

- 执行主机，例如中央服务器、训练服务器、RK3588 板卡或联网打包机。
- 当前目录。
- 需要的用户权限。
- 命令是否会中断服务或删除资源。

默认从项目根目录开始，必须切换目录时给出完整 `cd` 命令。多 Compose 文件始终显式写出
所有 `-f` 参数。生产镜像始终使用明确标签。示例变量使用 `<CENTRAL_SERVER_IP>`、
`<NODE_TOKEN>` 等占位符。

清理操作分级：

- 安全清理：停止并重建目标容器、删除悬空镜像、清理无引用构建缓存。
- 深度清理：删除指定旧标签或大范围构建缓存。
- 数据清理：删除卷或数据目录，必须独立成节并明确不可恢复风险。

## 9. 网络设计

网络章节按以下优先级编写：

1. 局域网或路由可达时直接连接。
2. 跨网段长期部署使用 VPN。
3. 无法建立双向路由时使用 SSH 隧道。

每种模式说明端口映射、中央平台地址、节点注册地址、双向连通检查和断线恢复。SSH 密钥
仅说明生成、授权、权限和持久化方式，不写入真实密钥内容。

## 10. 验收设计

验收分层执行：

- 宿主机：架构、Docker/Compose、磁盘、端口和时间同步。
- 中央服务：容器状态、就绪接口、Web 入口和持久卷。
- 训练节点：节点健康、平台注册和最小训练任务。
- CUDA：宿主机驱动、容器 GPU 可见性和 CUDA 任务。
- RK3588：NPU/MPP/RGA 设备、RKNN Runtime、运行时自检、转换和推理服务。
- 网络：节点到中央平台以及中央平台到节点的双向连通。
- 业务：数据集上传、训练、转换、模型部署、图片/视频/RTSP 推理和结果检查。

无法在通用环境复现的硬件或真实流媒体验收必须标记为“需在目标环境执行”，并提供命令和
预期结果，不以文档编写者的环境替代现场验收。

## 11. 运维与回滚

升级固定执行顺序为：查看状态与日志、备份 `.env` 和数据、准备指定版本镜像、仅重建目标
服务、执行分层验收、失败时恢复旧标签、成功后清理悬空资源。

故障排查按症状组织，至少覆盖构建失败、镜像架构错误、节点离线、令牌不一致、CUDA
不可见、RK3588 设备缺失、转换失败、推理无预览、隧道中断和磁盘占满。

## 12. 安全约束

- 管理员令牌和全局 Worker 令牌必须不同，且生产环境不得使用开发默认值。
- 每个直连节点使用独立节点令牌；该令牌必须与管理员令牌、全局 Worker 令牌及其他节点
  令牌不同。
- 节点 Compose 可将同一个独立节点令牌同时映射为 `RKNODE_NODE_TOKEN` 和
  `RKNODE_WORKER_TOKEN`，用于节点服务鉴权及兼容 Worker 回调。这属于同一节点内部的
  变量映射，不代表多个节点共享令牌。
- `.env` 文件建议设置为 `600` 权限并排除出版本控制。
- 文档和命令输出不得包含真实密码、令牌或私钥。
- 对外暴露服务时配合防火墙、VPN 或受控反向代理。
- 删除卷、数据目录或全部缓存前必须单独确认目标范围。

## 13. 完成标准

- `docs/system-guide.md` 能由首次部署人员按顺序独立执行。
- 所有文件路径、服务名、环境变量和脚本在当前仓库中存在。
- 中央、训练、RK3588、网络和离线部署均有成功判定。
- 在线构建、已有镜像部署、清理、升级和回滚均有完整命令。
- 端到端验收明确区分通用验证和目标硬件现场验证。
- 文档不存在真实基础设施凭据和隐式 `latest` 生产部署命令。
- 与 `README.md`、`docs/simple-node-deployment.md`、`docs/offline-deployment.md` 的引用关系清晰，
  不产生相互矛盾的部署指令。
